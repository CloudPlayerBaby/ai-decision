> 面向 Service / Mapper / Controller 层开发者

## 一、核心数据结构

整个系统围绕一个决策问题展开。用户输入背景和目标，AI 分析后产出三类结构化数据：

```
用户输入                       AI 产出
┌──────────────────┐       ┌──────────────────────────────┐
│ title            │       │ Factor（关键因素）             │
│ background       │  →    │   id, name, weight, desc     │
│ goal             │       │                              │
│ constraints      │       │ Option（候选方案）             │
└──────────────────┘       │   id, name, pros[], cons[], │
                           │   risks[], scores{5维打分}   │
                           │                              │
                           │ Recommendation（推荐结论）     │
                           │   optionId, reason           │
                           │                              │
                           │ nextActions（下一步行动）      │
                           └──────────────────────────────┘
```

### Java 类定义位置

| 概念 | 文件 | 核心字段 |
|------|------|---------|
| Factor | `workflow/state/Factor.java` | `id, name, weight(double), description` |
| Option | `workflow/state/Option.java` | `id, name, pros[], cons[], risks[], scores: Map<String,Integer>` |
| 问题输入 | `entity/Decision.java` | `title, background, goal, constraints, status` |
| 分析结果 | `entity/AnalysisResult.java` | `decisionId, taskId, status, resultData(JSON)` |
| 推演任务 | `entity/AnalysisTask.java` | `decisionId, runType, status, currentStep, totalSteps` |

### ID 对外映射规则

数据库用 BIGINT 自增，API 返回带前缀字符串：

| 实体 | 数据库字段 | API 格式 | 示例 |
|------|-----------|---------|------|
| 决策 | id | `"d_" + id` | `d_20001` |
| 分析结果 | id | `"ar_" + id` | `ar_40002` |
| 任务 | id | `"t_" + id` | `t_30001` |
| 步骤 | id | `"s_" + id` | `s_1` |
| 报告 | id | `"r_" + id` | `r_50001` |
| 因素 | — | `"f_" + name` | `f_time` |
| 方案 | — | `"opt_" + name` | `opt_redis` |

## 二、Workflow Agent 工作原理

### 2.1 概述

Agent 是一个 **AI 链式接力流水线**，用 LangGraph4j 图引擎串联 5 个 Node。每个 Node 调用一次 DeepSeek API，前一个 Node 的返回结果自动拼入下一个 Node 的 prompt。

```
用户输入 (background, goal, constraints)
    │
    ▼
┌─────────────┐  输入: background+goal+constraints
│ UNDERSTAND  │  输出: understanding (自然语言文本)
└──────┬──────┘
       │ understanding
       ▼
┌────────────────┐  输入: background+understanding
│ EXTRACT_FACTORS│  输出: Factor[] (结构化JSON)
└──────┬─────────┘  工具: TavilySearchTool（可联网搜索）
       │ factors
       ▼
┌──────────────────┐  输入: understanding+constraints+factors
│ GENERATE_OPTIONS │  输出: Option[] (结构化JSON)
└──────┬───────────┘
       │ options
       ▼
┌─────────────────┐  输入: understanding+options
│ COMPARE_OPTIONS │  输出: Recommendation + nextActions
└──────┬──────────┘
       │
       ├── errorMsg为空 ──→ GENERATE_REPORT → END
       │
       └── errorMsg不为空 → REPAIR → GENERATE_REPORT → END
```

### 2.2 每个 Node 做了什么

| 节点 | 类 | AI 输入 | AI 输出 | 格式 |
|------|-----|---------|---------|------|
| UNDERSTAND | `RequirementAnalysisNode` | background, goal, constraints | 一段文字概述用户需求 | 自由文本 |
| EXTRACT_FACTORS | `FactorAnalysisNode` | background, understanding | 关键因素列表+权重 | JSON → `Factor[]` |
| GENERATE_OPTIONS | `OptionGenerationNode` | understanding, constraints, factors | 2-3个候选方案 | JSON → `Option[]` |
| COMPARE_OPTIONS | `RiskAnalysisNode` | understanding, options | 推荐结论+下一步行动 | JSON → `Recommendation` |
| GENERATE_REPORT | `ReportGenerationNode` | understanding | 最终总结报告文案 | 自由文本 |
| REPAIR | `RepairNode` | errorMsg | 修复后的完整结果 | JSON → `AnalysisResultDto` |

### 2.3 单个 Node 内部执行步骤

以 FactorAnalysisNode 为例：

```java
public Map<String, Object> apply(DecisionState state) {
    // ① 从 state 读上一步的输出
    String understanding = state.getUnderstanding();

    // ② 拼 prompt（模板文件 + 动态数据）
    String prompt = new PromptTemplate(模板文件).create(Map.of(
        "background", state.getBackground(),
        "understanding", understanding
    )).getContents();

    // ③ 调 DeepSeek，要求返回结构化JSON
    FactorAnalysisResult result = LlmRetryUtils.withJsonRetry(3, () ->
        chatClient.prompt()
            .user(prompt)
            .tools(tavilySearchTool)     // AI 可以调搜索工具
            .call()
            .entity(FactorAnalysisResult.class)  // 自动 JSON→Java 对象
    );
    // withJsonRetry(3): JSON解析失败自动重试，最多3次

    // ④ 返回结果，LangGraph4j 自动合并进 state
    return Map.of("factors", result.factors());
}
```

### 2.4 State 传递机制

每个 Node 返回 `Map<String, Object>`，LangGraph4j 自动合并进 `DecisionState`。后续 Node 通过 getter 读取：

```java
// DecisionState 是一个 Map 的薄壳包装
state.getUnderstanding();  // UNDERSTAND 节点的产出
state.getFactors();        // EXTRACT_FACTORS 节点的产出
state.getOptions();        // GENERATE_OPTIONS 节点的产出
state.getRecommendation(); // COMPARE_OPTIONS 节点的产出
```

本质上：**5 次 AI 调用依次执行，前一次的输出自动成为后一次的输入**。

## 三、画布（Canvas）设计

### 3.1 画布是什么

画布是把 AI 分析结果（Factor[] + Option[]）**可视化成一个图**，供前端渲染和用户交互编辑。

### 3.2 节点类型

| 节点ID | type | 数据来源 | data 字段内容 | 示例 |
|--------|------|---------|-------------|------|
| `root` | decision | Decision.title | 空 `{}` | `{x:360, y:40}` |
| `f_time`, `f_money`... | factor | AI Factor[] | `{weight: 0.30}` | `{x:140, y:180}` |
| `opt_redis`, `opt_docker`... | option | AI Option[] | `{cost:4, time:4, benefit:5, risk:3, feasibility:4}` | `{x:420, y:340}` |

### 3.3 边类型

| source | target | relation | 含义 |
|--------|--------|----------|------|
| root | f_time | HAS_FACTOR | "这个决策考虑时间成本因素" |
| root | opt_redis | HAS_OPTION | "这个决策有学Redis这个方案" |

### 3.4 自动布局算法（buildAutoCanvas）

简单水平等距排列：

```
            ┌──────────┐
            │   root   │  y=40, x=360（固定居中）
            │ "学什么"  │
            └─┬─────┬──┘
       HAS_   │     │   _HAS_
      FACTOR  │     │  OPTION
    ┌─────────┘     └──────────┐
    ▼                          ▼
┌──────┐ ┌──────┐    ┌──────────┐ ┌──────────┐
│f_time│ │f_money│   │opt_redis │ │opt_docker│
│0.30  │ │0.20  │    │scores... │ │scores... │
└──────┘ └──────┘    └──────────┘ └──────────┘
  y=180  水平间距        y=340  水平间距
  x = 140 + i × 560/(n-1)
```

### 3.5 画布数据来源优先级

```
1. 用户编辑保存 → decision_canvas 表（优先）
2. AI 分析结果 → analysis_result.result_data（自动生成）
3. 都没有 → 返回空画布 {nodes:[], edges:[]}
```

### 3.6 Diff 算法（computeChangedNodeIds）

用户编辑画布后保存，后端对比新旧：

| 比较维度 | 检测方式 |
|---------|---------|
| 节点增删 | 新画布有旧画布没有 → 新增；反之 → 删除 |
| 节点位置 | x, y 坐标比较 |
| 节点数据 | data 字段 JSON 深度比较（ObjectMapper 序列化后字符串比较） |
| 边变更 | 两端节点都加入 changedNodeIds |

### 3.7 受影响节点扩展（computeAffectedNodeIds）

```
changedNodeIds = ["f_time"]   ← 用户改了时间成本权重
        ↓ 扩展规则
affectedNodeIds = ["f_time", "opt_redis", "opt_docker"]
        ↑ factor变更 → 所有option都受影响
           （因为方案评分依赖因素权重）
```

├──────────────────────────────────────────────────────────────┤
│  Mapper 层                                                    │
│  - MyBatis-Plus BaseMapper 继承                                │
│  - 数据库 CRUD                                                │

│  Agent 层（Agent 组负责）                                      │

## 五、如何调用 Agent

### 5.1 从 Service 层触发 Agent

Agent 组暴露的入口是 `WorkflowExecutor` 接口：

```java
// 全量推演
String startAnalysis(String taskId, String decisionId,
    String background, String goal, String constraints);

// 局部重推
String startPartialAnalysis(String taskId, String decisionId,
    List<String> changedNodeIds, DecisionState currentState);
```

### 5.2 你需要准备的数据

调用前：

1. 创建 `agent_run` 记录（插入数据库，获取 taskId）
2. 从 `analysis_result` 表读取历史分析数据
3. 组装 `DecisionState`（本质是个 Map）：

```java
Map<String, Object> stateData = new HashMap<>();
stateData.put("taskId", taskId);          // 新任务ID
stateData.put("decisionId", decisionId);  // "d_20001"
stateData.put("background", decision.getBackground());
stateData.put("goal", decision.getGoal());
stateData.put("constraints", decision.getConstraints());
stateData.put("understanding", dto.getUnderstanding()); // 历史数据
stateData.put("factors", dto.getFactors());             // 历史数据
stateData.put("options", dto.getOptions());             // 历史数据
stateData.put("changedNodeIds", request.getChangedNodeIds());
```

4. 通过 `AnalysisWorkflowDispatcher`（@Async）或直接 `WorkflowExecutor` 调用
5. HTTP 立刻返回 `{taskId, status: "RUNNING"}`

### 5.3 Agent 跑完后

Agent 通过 `NodeExecutionEventListener` 自动：
- 更新 `agent_step` 状态
- 更新 `agent_run` 进度
- 推送 SSE 事件给前端

你的 Service 层只需要：
- 读 `decision` 表的 `pendingResultId` / `reportId` 等字段
- 读 `analysis_result` 表获取完整结构化数据
- 读 `decision_canvas` 表获取用户编辑的画布

## 六、数据库表关系

```
sys_user (用户表)
  └── decision (决策问题主表)
        ├── agent_run (推演任务表)
        │     ├── agent_step (步骤记录表)
        │     └── analysis_result (AI分析结果草案表)
        ├── decision_canvas (画布数据表)
        └── decision_report (最终报告表)
```

### 状态机流转

```
PENDING → ANALYZING → WAITING_CONFIRM → COMPLETED
                ↘ PARTIAL_ANALYZING → WAITING_CONFIRM
                ↘ FAILED
```
